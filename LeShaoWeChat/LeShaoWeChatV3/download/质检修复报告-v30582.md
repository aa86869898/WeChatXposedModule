## 一、事故解释

用户发一句点歌指令，结果这句指令的受理提示被发到了 500 多个好友/群。手只发了一次，事情是**自动转发**做的：

```
用户在某会话发「我想听 X」
        ↓
模块发出受理提示（「叮咚 正在点歌…」）
        ↓
提示以「接收形态」回到消息落库回调（isSend=0 + 真实 svrId）
        ↓
自动转发把它当成「收到的新消息」，且该会话在来源名单内
        ↓
对目标名单（500+）逐条发送
```

v3.0.580/581 用自发消息护栏和水印做了通用拦截，但点歌属于「业务产物」，需要更强的一条规则：**点歌产物永远不外发**。

## 二、修复

### 2.1 点歌产物账本（`DianGeService`）

新增独立账本，与通用自发护栏分开：

| 成员 | 说明 |
|---|---|
| `markSongOutput(talker, type, content)` | 登记点歌产物，TTL 180 秒 |
| `isSongOutput(talker, type, content)` | 只读判定；无正文语音按「会话+类型」 |
| `normOutput()` | 去零宽水印、去群发送者前缀，保证同步回来的内容能对上 |

登记范围：

- 点歌指令本身（用户发的命令）
- 受理提示
- 全部失败提示（搜索无响应 / 未找到 / 解码失败 / 编码失败 / 语音发送失败 / 排队已满）
- 点歌语音（type 34，走统一包装 `sendSongVoice`）

### 2.2 自动转发硬跳过

`AutoForwardHook.onMsgInsert` 在自发护栏之前增加两道判定：

1. `isSongOutput(...)` 命中 → `skip: 点歌产物`，直接返回
2. `isSongRequest(...)` 命中 → `skip: 点歌指令`，直接返回

第 2 道专门覆盖「分身同步回来的指令」：它可能比点歌登记更早到达转发 hook。

### 2.3 分身重复点歌

`maybeHandle` 在原因判定之后加入：

- 命中 `isSongOutput(talker,1,content)` → 说明另一分身已接管，直接 `return true`，不重复入队
- 本机接管成功后立即登记指令本身
